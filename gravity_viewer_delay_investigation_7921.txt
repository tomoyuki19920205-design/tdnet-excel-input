Viewer未反映原因の特定仕様書
目的
15:00開示銘柄（例: 7921 TAKARA & CO の 3Q）が、TDnet側では15:00に出ているのに、Viewerで15:19時点でも3Q PLが反映されていない原因を、推測ではなく実測ログとDB状態で特定する。
今回は修正実装が主目的ではなく、まず原因特定を最優先とする。

前提認識
- ユーザー環境では 15:00 にフラッパー付きで読みに行っているため、少なくとも「15:00開示を15:10まで検知していない」という前提ではない。
- したがって調査対象は「15:00以降にどの段階で止まっているか」の切り分けである。
- 今回は必ず対象銘柄を 7921 に固定し、必要なら同時刻帯の他銘柄も比較対象として使う。
- 原因が複数あってもよいが、最終的に「主因」「副因」を分けて整理すること。

調査ゴール
下記のどこで止まっているかを、時刻付きで確定すること。

経路
1. TDnet開示を検知できているか
2. ingest に取り込めているか
3. process 対象になっているか
4. financials 抽出に成功しているか
5. canonical / financials 系DBへ書けているか
6. api_latest_financials など Viewer参照面に出ているか
7. Viewer側取得・表示条件で落ちていないか

最終成果物
必須で以下を提出すること。

1. 事実ベースの時系列
   - 7921 3Q 15:00開示について、
     - 開示検知時刻
     - ingest登録時刻
     - process開始時刻
     - 抽出完了時刻
     - DB書込時刻
     - API view反映確認時刻
     - Viewer取得確認時刻
   を時系列で並べること

2. 原因分類
   下記のどれに該当するかを明示すること（複数可）
   - A. 検知漏れ
   - B. ingest未登録
   - C. queue投入漏れ / process未実行
   - D. 抽出失敗
   - E. DB書込失敗 / timeout / retry滞留
   - F. view側反映条件不整合
   - G. Viewer側取得条件 / period条件 / quarter条件 / ソート条件の不備
   - H. その他

3. 再発防止に必要な最小修正案
   - 大規模改修ではなく、今回の主因に対する最小変更
   - 変更箇所ファイル名
   - 想定影響
   - テスト観点

重要ルール
- 推測で終わらせず、必ずログ・DB・コードの3方向で裏を取ること
- 「たぶん」「可能性」だけで締めないこと
- 調査途中で原因候補が複数あっても、最後に優先順位をつけること
- ユーザーは“今まで一回も瞬時にPL反映されていない”と認識しているため、今回1件だけの偶発ではなく構造問題の可能性も意識すること
- ただし今回はまず7921の実例で事実確定を行うこと

調査ステップ
Step 1: 対象開示の同定
7921 TAKARA & CO の今回の3Q開示を、まずソース側で一意に特定すること。
確認項目:
- ticker / local code
- 開示種別
- 公表時刻
- TDnetのdoc id / filing id / URL / xbrl_url / pdf_url 等
- システム内での doc_type 判定結果

確認したいこと:
- 本当に対象開示が15:00にソース上に存在したか
- システムがそれをどのIDで認識すべきか
- 3Qとして扱うべき文書なのか

提出内容:
- 対象文書の一意キー一覧
- それぞれの値

Step 2: ingest まで到達しているか確認
対象文書が ingest 段階で取り込まれたか確認すること。

確認対象:
- pipeline_run.py ingest
- ingest関連ログ
- filings / raw_documents / queue系テーブルや永続化先
- stateファイルや seen 管理があればその状態

確認ポイント:
- 15:00以降、対象文書が ingest ログに出ているか
- skipされていないか
- duplicate扱いで落ちていないか
- doc_typeフィルタで除外されていないか
- correction / supplement と誤認されていないか

特に見たいこと:
- “見つけたが投入していない” パターンがないか
- 同一キー扱いで既存文書に潰されていないか
- 15:00フラッパー実行ログと ingest 結果の対応

提出内容:
- ingestログ抜粋
- ingestされた / されていないの判定
- その理由

Step 3: process 対象になっているか確認
ingest済みなら process に回ったか確認すること。

確認対象:
- job_queue / rebuild_queue / pipeline_runs
- process実行ログ
- filingごとの status 遷移

確認ポイント:
- queueに積まれているか
- stuck / pending / skipped / failed になっていないか
- lock競合で遅れていないか
- 先行ジョブ滞留で7921の処理開始が遅れていないか
- processが起動しても対象文書を拾えていないことがないか

必須観点:
- 7921の処理開始時刻
- 15:00から何分後に process 開始したか
- 他銘柄に埋もれて後回しになっていないか

提出内容:
- 対象文書の queue / status 遷移
- process開始遅延の有無
- 遅延があればその根拠

Step 4: 抽出成功 / 失敗の確認
processに入っているなら、financials抽出が成功したか確認すること。

確認対象:
- src/extractor.py
- XBRL抽出ログ
- PDF抽出ログ
- fallbackログ
- validator結果
- quarantine理由
- 生成payloadの中身

確認ポイント:
- XBRLあり / なし
- XBRL抽出成功 / 失敗
- PDF fallbackに入ったか
- PDF text抽出はできたか
- sales / operating_profit / ordinary_profit / net_profit のどこまで取れたか
- quarter判定（3Q）が正しいか
- 単位変換が壊れていないか
- 抽出成功しているのに downstreamで捨てられていないか

必須確認:
- 対象7921について、抽出結果JSONまたは中間データを実際に出すこと
- 「何が取れたか」「何がNoneか」を表で示すこと
- validatorや completeness 判定で落ちたなら、その条件式まで追うこと

提出内容:
- 抽出ルート（XBRL / PDF / その他）
- 抽出結果
- 失敗理由または成功根拠
- 3Q判定の根拠

Step 5: DB書き込みの確認
抽出できているなら、DB反映されているか確認すること。

確認対象:
- financials
- canonical_financials
- api_latest_financials の元テーブル
- 書き込みログ
- timeout / retry / upsert conflict ログ
- source priority / row_number / coalesce ロジック

確認ポイント:
- 7921 / 対象period / 3Q の行が insert or upsert されているか
- 書込時に timeout が出ていないか
- retry後に成功したか
- 既存レコードに負けて潰されていないか
- 4Q / 通期 / 前年同Q など別レコードと衝突していないか
- ticker正規化不一致（7921 vs 79210 等）がないか
- quarter列の表記揺れ（3Q / Q3 / third_quarter 等）がないか

必須確認SQL観点
少なくとも以下の観点を確認すること。
- 対象tickerの financials 生行一覧
- 対象tickerの canonical_financials 生行一覧
- period + quarter + source の組み合わせ
- 対象時刻直後に新規行が存在するか
- 既存行との競合有無

提出内容:
- どのテーブルに何行あるか
- 書込成功 / 失敗
- 失敗ならエラー内容
- 成功しているのに Viewerに見えないならその先へ進む

Step 6: View/API面で落ちていないか確認
DBに書けているなら、api_latest_financials 等の view で見えているか確認すること。

確認対象:
- api_latest_financials 定義
- row_number / partition / order by
- source priority
- quarter, period, disclosed_at, updated_at の扱い

確認ポイント:
- 7921 3Q行が view に出る条件を満たすか
- 別ソースの古い行が勝っていないか
- period 解釈違いで落ちていないか
- 3Qのはずが2Qや通期扱いに寄っていないか
- updated_at順ではなく別条件で旧データが優先されていないか

過去の既知問題を明確に再確認すること:
- period mismatch（pubdate vs fiscal year end）
- source列の参照不整合
- row_numberの並び順
- COALESCEで null 上書き / 非null消失
- 既存ビュー条件が最新四半期を正しく拾えているか

提出内容:
- 生テーブルにはあるか
- viewにはあるか
- viewにない場合の条件式上の理由

Step 7: Viewer側の取得・表示条件確認
API/viewに存在するなら、Viewer側で落としていないか確認すること。

確認対象:
- lib/viewer-api.ts
- FinancialsTable.tsx
- SegmentTable.tsx
- クライアント側整形ロジック
- period/quarterフィルタ
- sort/order
- キャッシュや再取得タイミング

確認ポイント:
- 7921でAPIレスポンスに3Qが含まれているか
- 画面表示直前のデータに3Qが残っているか
- フィルタで弾いていないか
- 旧年度データとの混在で隠れていないか
- 期間ソートの問題で2Qが先に見えているだけではないか
- SWR/ISR/ブラウザキャッシュ/サーバーキャッシュ等で古いデータを見ていないか
- 再フェッチ条件が弱く、更新後もしばらく古いレスポンスを出していないか

必須ログ
すでにあるなら活用、なければ一時追加してよい。
- [SEG-DEBUG-SERVER]
- [SEG-STAGE-1 raw]
- [SEG-STAGE-2 before/after-filter]
- [SEG-STAGE-3 segmentNames]
に相当する、financials版の実データログを出すこと

提出内容:
- APIレスポンス時点では存在したか
- 画面整形後に消えたか
- 最終描画データに3Qがあるか

Step 8: 構造問題の有無の確認
今回1件だけでなく、「今まで一回も瞬時にPL反映されていない」というユーザー認識が事実かを軽く確認すること。

方法:
- 同日 or 直近数日で15:00開示銘柄を数件サンプル抽出
- 開示時刻から Viewer反映確認時刻までの遅延を比較
- 平均 / 最頻 / 最悪をざっくり出す

目的:
- 7921個別不具合なのか
- パイプライン全体の構造的遅延なのか
を切り分ける

提出内容:
- サンプル数件の遅延比較
- 7921が例外か通常か

調査時の具体チェック項目
必ず以下を確認すること。

A. 文書識別
- 7921で local code 正規化不一致はないか
- doc_type が financial_statement 扱いか
- 3Q判定が quarter=3Q として落ちているか

B. フィルタ除外
- correction/supplement/forecast_revision 等と誤分類されていないか
- “決算短信でない” 判定に入っていないか
- タイトル判定で落ちていないか

C. 抽出
- XBRL URL が存在するか
- XBRL archive/cache に載っているか
- PDF text が空になっていないか
- OCR未実装が原因で text抽出不可になっていないか
- 売上・営業利益ともに None で捨てられていないか

D. DB
- financials にはあるが canonical にない、のような段差がないか
- upsert timeout / retryで遅延していないか
- unique key競合で消えていないか
- source priorityで旧データが勝っていないか

E. Viewer
- api_latest_financials にはあるが表示されない、が起きていないか
- period/quarter条件で除外されていないか
- フロントで stale cache が残っていないか

- 主因:
- 副因:

実装はまだしなくてよいもの
今回は原因特定が先なので、以下は調査段階では未着手でよい。
- 常駐化
- 大規模リアルタイム化
- OCR本実装
- パイプライン全面再設計
- UI全面改修

ただし、原因特定に必要な一時ログ追加は行ってよい。

必要なら一時追加してよいログ
対象7921についてのみでよいので、下記ログを入れて可視化してよい。
- ingestで見つけた瞬間のdoc id / code / title / published_at
- process投入時のqueue log

- 抽出結果の主要PL項目
- DB upsert対象 payload

補足
ユーザーの問題意識は「15:00開示が15:19でもPLに出ないのはおかしい」「しかも今まで瞬時に反映されたことがない」である。
したがって、7921単体の失敗だけでなく、同種の遅延が恒常化しているならその事実も必ず報告すること。
特に、「検知は早いが downstream が遅い」のか、「そもそも ingestされていない」のかを最優先で切り分けること。

この調査の完了条件
以下をすべて満たしたら完了とする。
- 7921の15:00開示について、どの段階で止まったか断定できる
- 根拠ログ・DB状態・コード箇所を提示できる
- 主因と副因を分けて説明できる
- 最小修正案まで出せる
