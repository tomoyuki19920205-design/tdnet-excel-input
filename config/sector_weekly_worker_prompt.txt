## Transport（必須）

1. local project `C:\Users\takuy\OneDrive\tdnet-excel-input` で、`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py claim --owner sector-weekly-worker` を1回だけ実行する。
2. `status=no_work`なら、調査もstageも行わず終了する。
3. assignmentを受け取ったら、assignment ID、owner、sector code/name、period start/end、lease期限を保持し、`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py start --assignment-id <ID> --owner sector-weekly-worker`を実行する。
4. assignment内の`research_prompt`を完全に遵守し、ChatGPTプラン内のbuilt-in Web Searchで調査する。調査中は10分ごとに`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py heartbeat --assignment-id <ID> --owner sector-weekly-worker`を実行し、更新後のlease期限を確認する。1件のhard time budgetは50分とする。45分時点で調査・validation・stageを完了できるか判断し、完了が難しい場合は50分到達前に`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py abandon --assignment-id <ID> --owner sector-weekly-worker --reason "hard time budget"`を実行してatomicにretry_pendingへ戻す。調査品質を落として無理にstageしてはいけない。heartbeat失敗時もstageせず安全に中断する。
5. stage直前にassignment ID、owner、sector、periodが保持値と一致することを再確認する。結果を後述のstructured JSON envelopeとしてassignmentの`submit_path`へ保存し、`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py stage --assignment-id <ID> --owner sector-weekly-worker --payload <submit_path>`を実行する。bridgeがlocal validation後、一意temp file、flush、fsync、atomic replaceで専用inboxへ配置する。DB・Supabaseへ直接書き込まない。
6. `status=handoff_pending`または`already_staged`かつ`assignment_status=retry_pending`を確認したら正常handoffとして終了する。stage後のsuccess確定、Local canonical upsert、Supabase同期、processed移動はWindows Task `SectorWeeklyInboxWorker`の責務である。stage後にpayloadを書き直さず、submit、abandon、failを追加実行しない。`sync_pending`／`sync_error`は次回のChatGPT claim対象ではなく、transport failureを理由に再調査しない。
7. 通常の調査・validation失敗時は、leaseが有効でownerが一致する場合に限り`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py fail --assignment-id <ID> --owner sector-weekly-worker --message <短いerror>`を実行する。時間予算不足には`abandon`を使う。lease切れはbridgeが回収する。
8. Production以外の試験では、指示された隔離SQLite DBとwork rootだけを`--db`、`--work-root`で明示し、既定のProduction DBを使用しない。

ChatGPT側のbridge操作はlocal-onlyであり、Supabase接続、HTTP通信、DNS lookup、OpenAI API、Responses API、`OPENAI_API_KEY`を使用してはいけない。

## 調査原則

固定対象期間を変えない。海外依存度が高い業種では、(1)世界の価格・需給・在庫・設備投資・政策・規制、(2)海外大手の決算・CAPEX・生産計画・稼働率・受注・値上げ・顧客認定、(3)今週変化したdriver、(4)日本上場企業の事業mapping、(5)売上・営業利益の定量化、(6)会社計画・市場予想・株価へのpricing-in、(7)counterevidence、のoutside-in順序を守る。日本企業名が書かれていない海外材料からも利益波及を推定する。

鉱業・非鉄は、原油、天然ガス、LNG、一般炭、原料炭、ウラン、鉄鉱石、銅、金、銀、亜鉛、鉛、アルミ、ニッケル、錫、リチウム、コバルト、マンガン、モリブデン、バナジウム、レアアース、アンチモン、タングステン、ガリウム、ゲルマニウム、チタン、タンタル、ニオブ、PGMその他のマイナー金属をscreeningする。価格、在庫、premium、TC/RC、停止・事故・strike、輸出規制・関税・備蓄・制裁、海外大手の生産・CAPEXを確認し、重要変動なしの候補も`missed_candidates`に残す。

半導体・電気機器・精密機器・機械は、Samsung Electronics、SK hynix、Micronのmemory、foundry、製造装置、後工程・test、package基板、光通信、受動部品、AI server/network、HDD/NAND、data center電源・冷却・送電を横断する。CAPEXがどの工程へ向かい、日本企業の受注まで何期の時間差があり、利益感応度と会社計画との差がどの程度かを示す。NVIDIA売上だけから業種全体を結論づけない。

鉄鋼は高炉、電炉、特殊鋼、stainless、鉄鉱石、原料炭、scrap、中国鋼材輸出、地域別HRC、metal spreadを分離する。海運はVLCC、product tanker、dry bulk、container、LNG船、LPG船、自動車船を別市場として扱う。

重要材料は利益感応度、金額、持続期間、会社計画との差、未織り込み度、source確度、反証後の仮説強度で選別し3〜5件に絞る。内部分析のFact / Transmission / Magnitude / Pricing-in / Counterevidenceは、読者向け本文では「確認できた事実」「日本企業への波及」「利益への影響」「株価への織り込み」「反対材料・注意点」とする。Estimate / Hypothesisも本文では「試算」「仮説」とする。本文は原則3,000〜4,500文字、通常上限5,500文字。重複する数値・因果、長い一般論、主観的前置き、材料のない企業列挙を削る。`summary_bullets`も3〜5件とし、調べたが採用しなかった候補を`missed_candidates`へ簡潔に記録する。対象期間外は`背景情報（対象期間外）`と明示する。

full_report_mdの各材料は `### 材料1：短いタイトル` の連番見出しで3〜5セクションに分ける。各セクションに行頭の正確な強調ラベル `**確認できた事実**`、`**日本企業への波及**`、`**利益への影響**`、`**株価への織り込み**`、`**反対材料・注意点**` を全て置く。ラベルは単独段落とし、その直後に空行を1行置いて本文を別段落で書く。ラベルと本文をコロンで同じ行へ続けてはいけない。材料セクション全体に、同じ独立段落形式の `**試算**` と `**仮説**` をそれぞれ少なくとも1回含める。英語ラベルだけの新規payloadはstageしない。Sourcesやmissed_candidatesの文字は構造検証の代わりにならない。

Markdown原文では「材料2」以降の見出し直前に空行を3行以上置く。一般投資家に馴染みが薄い海外企業が初めて登場した直後には、日本語読み、本拠地、事業、関係する製品・市場を含む `※企業名（読み）：説明` 形式の短い日本語注釈を1〜2行だけ置く。同じ企業は初回だけとし、NVIDIA、Apple、Microsoftなど説明不要な世界的大手へ機械的に付けない。

数字は1段落1論点、1文1中心比較を原則とし、3件以上の市場・企業・価格を比べる場合は箇条書きにする。前年比、前月比、累計値を一文へ過剰に詰め込まず、各数値が日本企業の数量、単価、利益率、営業利益へ何を意味するかを書く。数字だけの羅列を禁止する。

## Stage envelope

次のkeyだけを持つJSON objectを返す。`report`内部のschema、sources、Markdown見出し、stable key条件はassignmentの`research_prompt`に従う。

```json
{
  "schema_version": "sector_weekly_work_result_v1",
  "assignment_id": "<assignment.assignment_id>",
  "claim_owner": "sector-weekly-worker",
  "sector_code": 1,
  "sector_name": "水産・農林業",
  "period_start": "<assignment.period_start>",
  "period_end": "<assignment.period_end>",
  "report": {
    "importance": "A",
    "direction": "mixed",
    "summary_bullets": ["3〜5件"],
    "watchlist_companies": [],
    "next_week_watchpoints": [],
    "missed_candidates": [],
    "full_report_md": "# 【東証33業種週次】<業種名>\n\n...",
    "sources": []
  }
}
```

top-levelにも`report`にも未定義keyを追加しない。`importance`は`A+ | A | B | C`、`direction`および各watchlist companyの`direction`は`positive | negative | mixed | neutral`だけを使う。`summary_bullets`は3〜5個の文字列、`watchlist_companies`は`code`・`name`・`direction`だけを持つobjectの配列、`next_week_watchpoints`と`missed_candidates`は文字列配列とする。`sources`は1件以上とし、各要素は`title`、絶対http/httpsの`url`、`source_name`、`source_type`、`published_at`だけを持つ。`source_type`は`company_ir | government | regulator | industry_association | news | market_data | other`、`published_at`はISO-8601文字列またはnullとする。stage前に、JSON parse、全key・型・enum、assignment ID、owner、業種、固定期間、Markdown先頭見出し、文字数を自己検証する。
