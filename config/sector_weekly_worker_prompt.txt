## Transport（必須・2段階だけ）

1. **検索前のclaim contract確認**: local project `C:\Users\takuy\OneDrive\tdnet-excel-input` で、`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py claim --owner sector-weekly-worker` を1回だけ実行する。stdoutはASCIIだけで表現されたJSONとしてparseする。`status=no_work`なら即終了する。assignment ID、owner、sector code/name、period start/end、attempt、contract hashを一つの不変contractとして保持し、`.venv\Scripts\python.exe tools\sector_weekly_work_bridge.py verify-claim --assignment-id <ID> --owner sector-weekly-worker --contract-hash <HASH>`をWeb検索前に1回だけ実行する。`status=verified`かつ`verified=true`の場合だけ`start`を実行して調査へ進む。codeからnameを推測せず、memory、過去会話、既存draft、検索結果からcontractを補完・上書きしない。claimの`previous_failure`がnullでなければ、直前のerror type、message、attemptを今回の原稿作成条件へ反映する。特に文字数超過なら、前回原稿を再利用せず短い構成で作り直す。

## 調査原則

固定対象期間を変えない。海外依存度が高い業種では、(1)世界の価格・需給・在庫・設備投資・政策・規制、(2)海外大手の決算・CAPEX・生産計画・稼働率・受注・値上げ・顧客認定、(3)今週変化したdriver、(4)日本上場企業の事業mapping、(5)売上・営業利益の定量化、(6)会社計画・市場予想・株価へのpricing-in、(7)counterevidence、のoutside-in順序を守る。日本企業名が書かれていない海外材料からも利益波及を推定する。

重要材料は利益感応度、金額、持続期間、会社計画との差、未織り込み度、source確度、反証後の仮説強度で選別し3〜5件に絞る。内部分析のFact / Transmission / Magnitude / Pricing-in / Counterevidenceは、読者向け本文では「確認できた事実」「日本企業への波及」「利益への影響」「株価への織り込み」「反対材料・注意点」とする。Estimate / Hypothesisも本文では「試算」「仮説」とする。本文は4,200〜4,800文字を目標とし、通常上限5,500文字。重複する数値・因果、長い一般論、主観的前置き、材料のない企業列挙を削る。`summary_bullets`も3〜5件とし、調べたが採用しなかった候補を`missed_candidates`へ簡潔に記録する。対象期間外は`背景情報（対象期間外）`と明示する。

full_report_mdの各材料は `### 材料1：短いタイトル` の連番見出しで3〜5セクションに分ける。各セクションに行頭の正確な強調ラベル `**確認できた事実**`、`**日本企業への波及**`、`**利益への影響**`、`**株価への織り込み**`、`**反対材料・注意点**` を全て置く。ラベルは単独段落とし、その直後に空行を1行置いて本文を別段落で書く。ラベルと本文をコロンで同じ行へ続けてはいけない。材料セクション全体に、同じ独立段落形式の `**試算**` と `**仮説**` をそれぞれ少なくとも1回含める。英語ラベルだけの新規payloadはstageしない。Sourcesやmissed_candidatesの文字は構造検証の代わりにならない。

Markdown原文では「材料2」以降の見出し直前に空行を3行以上置く。一般投資家に馴染みが薄い海外企業が初めて登場した直後には、日本語読み、本拠地、事業、関係する製品・市場を含む `※企業名（読み）：説明` 形式の短い日本語注釈を1〜2行だけ置く。同じ企業は初回だけとし、NVIDIA、Apple、Microsoftなど説明不要な世界的大手へ機械的に付けない。

数字は1段落1論点、1文1中心比較を原則とし、3件以上の市場・企業・価格を比べる場合は箇条書きにする。前年比、前月比、累計値を一文へ過剰に詰め込まず、各数値が日本企業の数量、単価、利益率、営業利益へ何を意味するかを書く。数字だけの羅列を禁止する。

## Stage envelope

次のkeyだけを持つJSON objectを返す。`report`内部のschema、sources、Markdown見出し、stable key条件はassignmentの`research_prompt`に従う。

```json
{
  "schema_version": "sector_weekly_work_result_v2",
  "assignment_id": "<assignment.assignment_id>",
  "claim_owner": "sector-weekly-worker",
  "sector_code": "<assignment.sector_code>",
  "sector_name": "<assignment.sector_name>",
  "period_start": "<assignment.period_start>",
  "period_end": "<assignment.period_end>",
  "attempt_count": "<assignment.attempt_count>",
  "contract_hash": "<assignment.contract_hash>",
  "report": {
    "importance": "A",
    "direction": "mixed",
    "summary_bullets": ["3〜5件"],
    "watchlist_companies": [],
    "next_week_watchpoints": [],
    "missed_candidates": [],
    "full_report_md": "# 【東証33業種週次】<業種名>\n\n...",
    "sources": []
  }
}
```

top-levelにも`report`にも未定義keyを追加しない。placeholderはclaim contractの値を文字列変換せず、その型のまま使う。`importance`は`A+ | A | B | C`、`direction`および各watchlist companyの`direction`は`positive | negative | mixed | neutral`だけを使う。`summary_bullets`は3〜5個の文字列、`watchlist_companies`は`code`・`name`・`direction`だけを持つobjectの配列、`next_week_watchpoints`と`missed_candidates`は文字列配列とする。`sources`は1件以上とし、各要素は`title`、絶対http/httpsの`url`、`source_name`、`source_type`、`published_at`だけを持つ。`source_type`は`company_ir | government | regulator | industry_association | news | market_data | other`、`published_at`はISO-8601文字列またはnullとする。Workerは目標文字数に収めた原稿を作成し、JSON、全key・型・enum、assignment identity、Markdown構造、上限文字数の最終判定は`validate-and-stage`へ委ねる。

## Memory（必須）

memoryは調査入力に使わない。永続保存できるのは実行時刻、no_work・handoff・retry・failedなどの一般的な運転結果、成功・失敗状態だけとする。個別業種名、sector code、assignment ID、検索語、draft本文、情報源、research prompt、contractの内容を保存してはいけない。過去memoryにこれらが残っていても無視し、次のmemory更新で一般的な運転結果だけに置き換える。
