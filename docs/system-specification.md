# TDNET Alerts & Company Viewer システム仕様書

## 1. 全体構成
本システムは、TDNETからの適時開示情報の取得・解析と、J-Quantsデータなどを統合した財務情報ビューアを提供するWebアプリケーションおよびバックエンドパイプラインです。

- **TDNET Alerts画面**: 適時開示（決算短信や業績修正など）の通知を一覧表示し、YOY（前年同期比）などの指標を可視化するフロントエンド画面。
- **Company Viewer画面**: 指定した銘柄の過去の財務データ、セグメント情報、および将来の予想データ（J-Quants/TDNET）を比較・編集可能なスプレッドシート状のUIを提供するフロントエンド画面。
- **Supabase**: バックエンドデータベース（PostgreSQL）。`financials`, `canonical_financials`, `tdnet_events` 等のテーブルで構成され、データ蓄積およびAPI（PostgREST）を提供する。
- **Vercel**: Next.jsフロントエンドアプリケーションのホスティングおよび本番環境へのデプロイメント環境。
- **GitHubリポジトリ**: ソースコードのバージョン管理およびVercelとの連携によるCI/CDパイプライン。
- **ローカル処理スクリプト**: Pythonによるデータ抽出、TDNETからのPDF/XBRL解析、DBへのバッチ投入・修復処理などのバックエンド業務を担うスクリプト群。
- **データ抽出パイプライン**: TDNETからのイベント検知 → PDF/XBRLデータ抽出 → DB保存 → `financials` への同期 → UI表示のための `compare_json` 生成という一連の流れ。

## 2. 重要URL・環境
- **本番URL**: `https://company-memo-app.vercel.app/tdnet-alerts`
- **Vercelプロジェクト名**: `company-memo-app` (エイリアス: `company-memo-app.vercel.app`)
- **GitHubリポジトリ**: `https://github.com/tomoyuki19920205-design/tdnet-excel-input.git`
- **対象ブランチ**: `main` ブランチが本番環境と直結。
- **Supabase主要テーブル・ビュー**:
  - `tdnet_events`: TDNETの開示イベントを保存。
  - `financials`: PLや各種数値を保存する主要テーブル（Company Viewerのベース）。
  - `canonical_financials`: 業績修正などを反映した確定版の財務データ（正規化データ）。
  - `api_latest_financials_canonical`: 各銘柄の最新FYの財務数値を算出するビュー。
- **ローカル開発時の起動方法**:
  - `web` ディレクトリで `npm run dev` 
  - ブラウザで `http://localhost:3000` にアクセス

## 3. UI仕様
### /tdnet-alerts の画面構成
- **左側ペイン（通知欄）**: 新着のTDNETイベントカードが時系列にリスト表示される。
- **右側ペイン（メイン表示）**: イベント詳細やCompany Viewerを切り替えて表示するエリア。

### 左側通知欄の仕様
- **日付フィルタ**: 特定の日付のイベントのみを絞り込む。
- **カテゴリボタン**: 「決算」「業績修正」「配当」「自己株式取得」などのイベントカテゴリごとにフィルタリング。
- **全期間ON/OFF**: デフォルトでは最近の期間に絞られているが、ONにすると過去すべてのイベントを検索対象にする。
- **通知カードクリック時の動作**: カードをクリックすると右ペインの「イベント詳細タブ」が開き、該当イベントのデータやPDFリンク等が表示される。

### 右側Company Viewerの表示仕様
- **イベント詳細タブ**: クリックされた通知カードの詳細情報（抽出されたXBRL/PDFの数値等）を表示。
- **Company Viewerタブ**: 対象銘柄の財務データをスプレッドシート形式で表示。
- **初期表示仕様**: 通知カード未選択時は「開示をクリックすると右側に Company Viewer が表示されます」という案内が表示される。（※意図的な設定。全体表示崩れを防ぐため）

## 4. Company Viewer仕様
- **検索欄**: ティッカーシンボルや社名を入力して銘柄を検索・表示。
- **ticker検索**: 4桁の英数字（例: 7203, 186A）を入力して表示データを切り替え。
- **PL表示**: 売上、営業利益、経常利益、純利益などの損益計算書項目を年度/四半期ごとに表示。
- **セグメント表示**: 企業が報告している事業セグメントごとの売上・利益内訳。
- **メモ行**: 各期に対する自由記述のメモエリア。
- **手入力メモ**: UI上から直接セルの数値を修正・追記できる機能。
- **データソース切替**: canonical, financials, J-Quants等のソース優先度切替。
- **表示色・枠線・編集操作**: 編集されたセルは色が変わるなど、変更箇所が視覚的に分かるUI。
- **Excelコピー/ペースト仕様**: スプレッドシートからExcelへのコピペ、またはExcelからのペーストに対応するためのTSV形式クリップボード連携。

## 5. 通知カード仕様
- **表示項目**: 企業名、ティッカー、発表時刻、イベント種別、比較用YOYハイライト。
- **売上YOY / 営利YOY**: 売上高および営業利益の前年同期比。
- **比較YOY**: イベント発表前と発表後の業績予想の増減率。
- **1Q/2Q/3Q/4Q/FYごとの比較ロジック**: 発表された四半期がどこに属するかを判定し、前年の同四半期、または前回発表の通期予想と比較する。
- **色分けルール**: ポジティブサプライズ（例: +5%以上）は緑、ネガティブサプライズは赤など、閾値に基づくカラーリング。
- **データ連携**: `raw_payload`（抽出元の生データ）、`notification_compare_json`（YOY比較のために計算されたJSON）、`extracted`（正規化された抽出値）を使用してUIを描画。

## 6. データ抽出仕様
- **TDNET取得**: 適時開示システムからの新規イベントクローリング。
- **PDF抽出**: XBRLが存在しない開示（配当や自己株式取得など）におけるLLM/OCRを用いたテキスト・数値抽出。
- **XBRL抽出**: 決算短信等に添付されるXBRLからの構造化データ抽出。
- **J-Quants取得**: J-Quants APIを利用した実績および予想財務データの補完。数字5桁コードは英字ティッカー（186Aなど）に適切に正規化して扱う。
- **DB格納の流れ**:
  - `tdnet_events`: イベントメタデータの保存
  - `canonical_financials`: 抽出された決算数値を正規化して保存
  - `financials`: アプリケーション用に最適化されたPLデータ
  - `api_latest_financials_canonical`: YOY計算等に用いる最新FYビュー
- **修復処理・compare生成**: 過去データの欠損を埋めるYOY修復バッチ処理や、フロントエンド表示用の `compare_json` 生成処理。
- **既存compareの上書きルール**: 既存の `notification_compare_json` にユーザーの手修正等が入っている可能性があるため、**既存の比較データを無条件で上書きしない（再生成しない）** ことが厳格なルール。

## 7. デプロイ仕様
- **正しいVercelプロジェクト**: `company-memo-app`
- **正しいProduction Alias**: `company-memo-app.vercel.app`
- **GitHub経由デプロイとCLIデプロイの違い**:
  - GitHubへのPush（`main` ブランチ）は、自動的にCI/CDをトリガーし、正しい環境変数と設定でビルドされる。
  - CLIデプロイ（`vercel --prod`）をローカルディレクトリから実行すると、Vercelのプロジェクト設定を上書きしてしまったり、ローカル固有の未コミットキャッシュが紛れ込み、**画面崩れなどの原因になる危険性がある**。
- **今回事故った原因**: `web` ディレクトリでCLIの `vercel --prod` を実行した際、プロジェクト設定の不整合やキャッシュ影響によりTailwind等のCSSが正しく生成されず、さらに一時的に別プロジェクトへデプロイされたため。
- **本番反映前後の確認手順**: GitHubへPush後、Vercelダッシュボードで `company-memo-app` のビルド完了を待ち、必ず本番URL（`https://company-memo-app.vercel.app/tdnet-alerts`）をブラウザで開いて目視確認する。

## 8. 復旧手順
- **画面が崩れた場合**: 直ちにVercelの過去の正常なDeploymentへRollbackする。
- **Vercelの過去DeploymentへRollbackする手順**:
  1. `vercel ls company-memo-app` で正常だった過去のデプロイURLを確認。
  2. `vercel alias set <過去の正常なデプロイURL> company-memo-app.vercel.app` を実行し、エイリアスを向ける。
- **Git revert手順**:
  1. `git log` で原因となったコミットIDを特定。
  2. `git revert <コミットID>` を実行して打ち消すコミットを作成。
  3. `git push` を行い、正しい状態のコードをGitHub経由で自動デプロイさせる。
- **Supabaseデータ復旧**: `scratch/` や退避用テーブルにバックアップがある場合は、それを元にUPDATE/INSERTを行うスクリプトを作成して実行する。

## 9. 禁止事項
- **ローカル修正のみで完了報告しない**: 必ずGitへPushし、本番環境へのデプロイ完了を確認すること。
- **別Vercelプロジェクトへデプロイしない**: CLIを利用する場合は紐付け（link）を再確認し、原則としてGitHub Push経由の自動デプロイを優先すること。
- **本番URL確認なしで反映済みと言わない**: ターミナルのログが成功していても、必ず本番URLへアクセスした結果をもとに報告すること。
- **scratchスクリプトを増殖させない**: 使い捨ての調査スクリプトは `scratch/` ディレクトリ等にまとめ、プロジェクトルートを散らかさないこと。
- **既存compareを上書きしない**: `notification_compare_json` は一度生成されたら安易に再生成スクリプトで上書きしないこと。
- **raw_payloadの一部取得でnull化させない**: JSONBカラムを更新する際は、既存のキーを保持（マージ）し、誤って全体をnullや空にしないこと。
- **大きなリファクタを本番直投入しない**: 影響範囲が大きい変更は事前にDRY RUNを行い、確認のステップを挟むこと。

## 10. 完了報告ルール
デプロイを伴う作業の完了報告時は、必ず以下の項目を提出すること。

- **コミットID**: デプロイ対象となったコミットハッシュ。
- **Push先リポジトリ**: GitHubリポジトリURLと対象ブランチ。
- **Vercel Deployment URL**: 実際にビルドされたデプロイごとの一意なURL。
- **Production Alias URL**: ユーザーがアクセスする本番URL（`company-memo-app.vercel.app`）。
- **BEFORE/AFTER確認結果**: 修正前と修正後の差分の結果。
- **実際に確認できたこと**: 本番URLにアクセスして確認した動作や表示結果。
- **目視確認の制約**: AI実行環境による制約上、実際のブラウザ画面（CSSのレイアウト崩れ等）を目視確認できない場合は、その旨を報告に明記し、HTMLソース/データの到達確認を行った上で、最終的な目視確認をユーザーへ依頼すること。
