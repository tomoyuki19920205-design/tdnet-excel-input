# EDINET 有報 受注系データ抽出 本番実装仕様書

## 1. 最終検証結果
事前のスクラッチ検証における最終結果は以下の通りです。
- **検証対象**: 受注表が存在する企業50社
- **受注高取得成功**: 45社
- **受注残高取得成功**: 40社
- **誤抽出**: 0件
- **low判定（抽出失敗）**: 5社

表が存在する企業に限定した場合、90%という高い精度かつ誤抽出ゼロを達成しており、本番化に向けたロジックの信頼性が確認されました。

## 2. 本番化する抽出対象
以下の項目について、指定された抽出元からのみ値を取得します。
- **HTML tableからの受注高**
- **HTML tableからの受注残高**
- **HTML tableからの繰越工事高**
- **HTML tableからの完成工事高**
- **RPO（残存履行義務）** に限り、TextBlock内の自然言語文章（テキスト）からの抽出を許可する。

## 3. 本番で禁止する抽出
誤抽出（ノイズの混入）を防ぐため、以下の抽出処理は厳禁とします。
- **自然言語本文からの受注高抽出**（前年比の増減額等を誤って拾うリスクが高いため）
- **自然言語本文からの受注残高抽出**
- **前期比・前年比・増減額・構成比の取得**（これらが含まれる列・行はパース時にスキップする）
- **不確実な値の補完**（値が見つからない、または単位が存在しない場合は潔く `null` や `low` として扱う）

## 4. 正式化フェーズ案
本番パイプラインへの組み込みは、リスクを最小限に抑えるため段階的に行います。

- **Phase 1: scratch版維持** (完了)
  - ローカル検証用スクリプトとしての維持。
- **Phase 2: src配下に読み取り専用モジュール化**
  - 既存のパイプラインには組み込まず、`src` 配下に純粋なパースモジュールとして配置する。
- **Phase 3: JSON/CSV出力**
  - バッチ等で実行し、ファイル出力ベースで全体の挙動を確認する。
- **Phase 4: 手動確認**
  - 抽出されたJSON/CSVと実際の有価証券報告書を目視で突き合わせる。
- **Phase 5: DB保存設計**
  - テーブル構造等を設計する。
- **Phase 6: Viewer連携**
  - 最終的にフロントエンド（Viewer）側に表示させ、APIエンドポイントを整備する。

## 5. DB保存する場合の未決事項
Phase 5（DB保存設計）において、以下の事項を決定・整理する必要があります。
- **保存先テーブル**: 新規テーブルを作成するか、既存の業績テーブルに格納するか。
- **ticker/doc_id/periodの扱い**: どの単位でデータを紐付けし、一意制約を持たせるか。
- **単位変換**: 抽出元の単位（百万円、億円、千円など）をどう正規化してDBへ保存するか。
- **セグメント別データを保存するか**: 全社の「合計」行だけでなく、セグメント別の受注データも保存の対象とするか。
- **RPOを受注残高と分ける設計**: RPOは受注残高と会計上の認識基準が異なるため、同一カラムに混入させない設計をどう実現するか。
- **low/nullの保存方針**: 抽出不可や表が存在しない企業において、`NULL` で保存するのかレコードを作らないのか。
