# EDINET 有価証券報告書 受注系データ抽出 実装・検証ノート

## 1. 現時点の抽出方針
EDINETの有価証券報告書（XBRLファイル）から、特定のTextBlockタグを取得し、その内部にあるHTMLの表（`<table>`）または自然言語（テキスト）を解析して受注系の数値を抽出します。
対象タグは主に `ManagementAnalysisOfFinancialPositionOperatingResultsAndCashFlowsTextBlock` （経営者の財政状態、経営成績及びキャッシュ・フローの状況の分析）または `SignificantAccountingPoliciesTextBlock` 等です。

## 2. TextBlock中心で抽出する理由
受注高や受注残高といった指標は、EDINET（XBRL）の標準タクソノミとして独立した数値タグ（Numericタグ）が定義されていない、もしくは企業によって独自の拡張タグを使用しているケースが非常に多いためです。標準タグに頼るとほとんどの企業でデータが取得できません。そのため、経営分析のTextBlock内に記載されている表やテキストから物理的に抽出する方が確実性が高いと判断しました。

## 3. PDF座標抽出を使わない理由
PDFからの座標抽出は、表のレイアウト変更やフォントサイズの微妙な変化、改ページ等に対して非常に脆く、メンテナンスコストが膨大になります。一方、XBRL内のTextBlockはHTML構造を保持しており、`<table>` や `<tr>` といったセマンティックなタグからデータをパースできるため、座標抽出よりもはるかに堅牢で柔軟に対応できます。

## 4. 抽出項目定義
- **orders_received (受注高)**: 当期の新規受注額。
- **order_backlog (受注残高)**: 期末時点で未消化となっている受注残額。
- **construction_carryover (繰越工事高)**: 建設業等における次期への繰越工事額（実質的な受注残高と同義だが、明確に区別して保持）。
- **completed_construction (完成工事高)**: 建設業等における当期完成工事額（売上高相当）。
- **rpo (残存履行義務)**: IFRS適用企業が注記で開示する、未充足の履行義務総額。

## 5. RPOをorder_backlogに混ぜないルール
残存履行義務 (RPO) と受注残高は、性質が似ているものの会計基準上の厳密な定義や認識タイミングが異なります。分析時に異なる基準の数値が混在することを防ぐため、RPOは専用の `rpo` カラム（キー）に格納し、`order_backlog` には流用しないという厳格なルールを設けています。

## 6. v1で発生した誤抽出
最初の抽出ロジック（v1）では、以下のような前年比・増減率のパーセンテージ数値を誤って金額として取得してしまうケースが発生しました。
- **5631 日本製鋼所**: `order_backlog = -7` (前年同期比 △7.4% を誤取得)
- **6104 芝浦機械**: `order_backlog = -11` (前期比 △11.4% を誤取得)
- **7011 三菱重工業**: `order_backlog = 5` (前連結会計年度比 +5.8% を誤取得)

## 7. v2で修正した内容
上記v1の誤抽出を防ぐため、以下のロジック修正を行いました。
- **結合セル(colspan/rowspan)の正確な追跡**: ヘッダー行とデータ行でセル数が異なる場合、各行の colspan 合計値を計算し、動的なオフセット処理（ズレ補正）を導入。
- **パーセント表記列の徹底排除**: 列ヘッダーに「%」「％」「比」「率」「増減」のいずれかが含まれる場合、その列を金額カラムとしてマッピングする処理をスキップ。
- **データ取得時の保護層 (safe_parse)**: データセル内に「%」または「％」という文字列が含まれていた場合は、取得をキャンセルして `null` を返す保護処理を追加。
- **ヘッダー行の上書き防止**: 複数行にわたる複雑なヘッダーが存在する場合、一度見つけたヘッダーのインデックスが後続行のパースで上書きされてしまうバグを修正。

## 8. low判定5社の理由
抽出対象を31社とした DRY RUN (v2) において、5社は抽出不可（low判定）となりました。原因は以下の通りです。
- **1952 新日本空調**: （パーサー未対応）対象の表は存在するが、合計行の表記が「計」ではなく「第56期(2024年4月1日～…)」などとなっており、対象行としての条件にマッチしなかったため。
- **6981 村田製作所**: （パーサー未対応）表の1行目に「受注高」、2行目に「金額・構成比」とヘッダーが分かれており、「金額」列に「受注」の文字が含まれないため、マッピングの紐付けが切断されたため。
- **5985 サンコール**: （対象表なし）業績分析セクション内に「受注」という文字を含む表が存在しなかったため（本文で言及があるのみ）。
- **6101 ツガミ**: （対象表なし）同上。
- **7735 SCREENホールディングス**: （対象表なし）同上。

## 9. まだ未対応のケース
- **1952 新日本空調**: 建設系特有の「当期、前期」ではなく「第◯期」といった表記を行ヘッダーとするケースへの対応。
- **6981 村田製作所**: 階層化されたヘッダー（行や列がツリー状になっている表）において、親ヘッダーの名前（受注高）を子ヘッダー（金額）に継承させるセマンティックな表解析の実装。

## 10. 今後正式化する場合の方針
- 今回は `scratch/` として独立したローカルスクリプトで検証を行いましたが、正式機能化する際は、プロジェクトの抽出パイプラインに組み込む予定です。
- 本スクリプトのパース処理を関数化し、既存モジュールに統合します。
- DB保存およびSupabaseへの連携処理を実装し、Viewer側の表示画面で受注データを確認できるよう整備します。
- その際、未対応ケースについては無理に汎用化しすぎず、企業ごとのアダプタを書く方針も視野に入れます。

## 11. V3およびV4での追加修正と抽出結果
初期の課題を解決するため、V3およびV4にて以下の改善を行いました。
- **軽量グリッドパーサーの導入 (V3)**: HTMLの `rowspan` / `colspan` を完全に展開し、表を2次元配列（グリッド）として解析。多階層ヘッダーのコンテキスト継承を実現し、**6981 村田製作所** の抽出に成功しました。
- **行選択の優先順位スコアリング (V3)**: 行ヘッダーのテキストを解析し、「合計(100点) > 計(90点) > 全社(80点) > 当連結(70点) > 当事業(60点) > 第XX期(50点)」というスコアで評価するロジックを実装し、**1952 新日本空調** の「第56期」行の抽出に成功しました。
- **鹿島建設の合計行誤認識の修正 (V4)**: 行ヘッダーから数値・記号・空白を除去した純粋なテキストで判定するロジックに変更し、「計」に隣接する数値が混入してスコアを取り逃がす問題を解決しました。
- **単位（Unit）のフォールバック取得 (V4)**: 表内に「百万円」「億円」といった単位表記がない場合、表を包含する TextBlock 全体から「単位: 億円」などの表記を正規表現で探索して補完するロジックを実装し、**7013 IHI** の単位取得に成功しました。

**【V4 最終結果】**
- **対象社数**: 31社
- **成功社数**: 28社 (成功率 90.3%)
- **low判定**: 3社 (5985 サンコール, 6101 ツガミ, 7735 SCREEN)
これら3社については、有価証券報告書の該当セクション内に受注を示すHTMLテーブルがそもそも存在しないため、表解析のアプローチとしては取得不可（理論上の限界）であることが確認されました。逆に言えば、受注表が存在する会社においては概ね正確な抽出が可能であることが証明されました。
※ ただし本番パイプラインへの組み込み前には、異なる産業や別サンプルを用いた追加検証が必要です。
