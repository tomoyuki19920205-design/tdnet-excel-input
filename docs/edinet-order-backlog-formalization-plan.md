# EDINET 受注系データ抽出 正式化プラン (Formalization Plan)

## 1. 現在の検証結果
31社を対象とした検証スクリプト（V4）において、抽出成功率 **90.3%** を達成しました。
多階層ヘッダー、複雑な結合セル（colspan/rowspan）、および表の行見出しにおける「合計」「計」「当期」「第XX期」といった表記ゆれに対応するため、軽量グリッドパーサーと優先順位スコアリングアルゴリズムを導入し、誤抽出のリスクを事実上ゼロに近い水準まで抑え込んでいます。
また、値が存在しない（該当の表自体がない）3社については正しく low 判定とし、無理な抽出を行わない防御力も確認されています。

## 2. 本番組み込み前に必要な追加検証
現在の31社は、半導体製造装置や特定の機械・建設系に偏っている可能性があります。
本番環境の抽出パイプラインに組み込む前に、異なる産業や表の形式を持つ企業サンプルを用いて、グリッドパーサーおよび行スコアリングが意図通りに機能し、誤抽出を起こさないかを最終確認する必要があります。

## 3. 追加検証対象
次回以降の検証フェーズでは、今回未検証の「受注産業 50〜100社」を追加サンプルとして抽出精度を確認します。
特に以下の業種・カテゴリを中心に選定します。
- **中小型機械**
- **建設**
- **設備工事**
- **防衛**
- **造船**
- **SI (システムインテグレーション)**

## 4. DB保存設計に関する方針
現在の段階では「**DB保存設計はまだ行わないこと**」とします。
まずは様々なパターンの表からのデータ抽出が100%安全（False Positiveが発生しない）に実行できることを確約できる状態を構築することを最優先とします。

## 5. 正式化する場合の段階
EDINET受注系データ抽出機能の正式実装は、以下の段階（Phase）に分けて安全に進行します。

### Phase 1: scratch検証 (現在のフェーズ)
- 独立したローカルスクリプト (`scratch/extract_edinet_orders.py`) での実装と検証。
- アルゴリズムの精錬と追加検証対象（50〜100社）でのテスト。

### Phase 2: src配下に読み取り専用モジュール化
- `scratch/` で実績を積んだパーサー関数を、本番環境の `src/` 配下（例： `src/tdnet_parser/` や `src/extractor.py` の関連部分）に移動。
- 他のモジュールから安全に呼び出せるようカプセル化し、読み取り専用（副作用なし）の機能として組み込む。

### Phase 3: CSV/JSON出力
- 組み込んだ読み取り専用モジュールを用いて、実際のバッチ処理の一環として受注データを抽出。
- 結果は直接DBには書き込まず、まずは検証用・データレイク用途として CSV または JSON 形式で出力する。

### Phase 4: DB保存設計
- 出力された CSV/JSON が完全に要件を満たすことが確認できた後、初めてデータベースのスキーマ変更やマイグレーション方針を策定。
- Supabase のテーブルへ `orders_received`, `order_backlog` などのカラムを追加し、安全に保存するパイプラインを構築。

### Phase 5: Viewer連携
- DBに保存された受注系データを、フロントエンドの Viewer（tdnet-alerts 等の画面）で表示するための API と UI の改修を実施。
